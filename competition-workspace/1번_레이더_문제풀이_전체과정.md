# 1번 문제: Codex로 레이더 이동 표적 분류를 푼 전체 과정

> 대상 문제: **「레이더 시계열 데이터 기반 이동 표적 식별하기」**  
> 대회 작업일: 2026-10-10 / 문서 작성일: 2026-10-25  
> 이 문서는 문제 지문, 당시 대화·실행 로그, 실험 코드, 저장된 예측 배열, 최종 제출 파일을 대조해 작성했다. 새 모델을 학습하거나 제출 후보를 바꾸지는 않았다.

최종 풀이의 핵심은 **여러 레이더 관측값을 표적 하나의 특징표로 바꾸고, 사전학습된 TabICL을 이 대회 데이터에 맞게 미세조정한 뒤 여러 예측 확률을 평균한 것**이다. 개발용 5분할 교차검증에서 **1,000개 중 893개를 맞혀 89.3%**를 얻었다. 다른 분할로 같은 방식을 다시 평가했을 때는 **88.5%**였다. 두 수치는 훈련 데이터로 계산한 개발 검증 결과이며, 정답이 공개되지 않은 테스트 300개의 공식 점수는 확인되지 않았다.

처음부터 이 모델을 선택한 것은 아니다. ExtraTrees·CatBoost로 시작했고, 물리 지식을 이용한 특징, 이상치에 강한 특징, 센서별 보정, 점군 딥러닝, 여러 표형 데이터 모델, 클래스별 전문 모델, 의사 라벨까지 비교했다. 마지막에는 온라인 Notebook 안에서 다시 학습하는 CPU 대안도 시험했지만, 정확도가 낮아 사용자가 기존 GPU 계산 결과를 유지하기로 결정했다.

## 읽는 순서

- **1~4절:** 문제와 데이터, 검증 방식, 최초 기준 모델
- **5~8절:** 특징 개선과 다양한 모델의 시행착오
- **9~11절:** 최종 미세조정·앙상블·오류 분석
- **12~14절:** CPU 재학습 비교, 제출 파일 제작, 실행 확인
- **15~16절:** 재현에 필요한 파일과 해석상 한계
- **부록:** 보존된 5클래스 OOF 산출물 100개 전체의 점수와 특징 구성

## 1. 무엇을 맞히는 문제였나

### 1.1 한 행이 아니라, 한 표적의 관측 묶음을 분류한다

레이더가 약 500ms 동안 같은 이동 표적을 관측한다. 이때 레이더에 잡힌 점 하나를 **detection**, 같은 표적에서 모은 detection 묶음을 **sample**이라고 생각하면 된다.

예를 들어 `TR_000001`이라는 표적에 관측값이 20행 있다면, 20개 정답을 만드는 것이 아니라 **20행을 함께 보고 정답 하나**를 만든다. 시험에서 점수가 부여되는 단위도 `sample_id` 하나다.

분류할 클래스는 다음 5개였다.

| 정답 문자열 | 쉬운 설명 |
| --- | --- |
| `LIGHT_VEHICLE` | 승용차급 일반 차량 |
| `HEAVY_VEHICLE` | 대형 차량 |
| `TWO_WHEELER` | 자전거·오토바이류 |
| `PERSONNEL` | 보행자 한 명 |
| `PERSONNEL_GROUP` | 여러 명의 보행자 |

훈련 파일에는 정답이 있고, 테스트 파일에는 정답이 없다. 최종 산출물은 테스트 표적 300개의 `sample_id,label` 두 열을 가진 `submission.csv`다. ID마다 정확히 한 행이 있어야 하며 ID 오름차순으로 저장해야 했다.

지문에서 테스트를 ‘검증 데이터’라고 부르기도 하지만, 이 문서에서는 혼동을 피하기 위해 **정답 없는 300개를 테스트**, 훈련 1,000개를 나누어 성능을 측정하는 절차를 **개발 검증**이라고 부른다.

근거: [사용자가 실행한 원래 이름의 Notebook](<레이더 시계열 데이터 기반 이동 표적 식별하기.ipynb>).

### 1.2 레이더 열은 어떤 의미인가

| 열 | 의미 | 분류에 활용할 수 있는 정보 |
| --- | --- | --- |
| `sample_id` | 표적 관측 묶음 ID | 관측값을 묶고 제출 행을 연결한다. 숫자 순서 자체를 예측 특징으로 쓰지는 않았다. |
| `t_ms` | 관측 시작 후 경과 시간 | 위치·반사 강도·속도가 시간에 따라 어떻게 변하는지 계산한다. |
| `sensor_id` | 관측 센서 번호 | 어느 센서에서 얼마나 관측했는지, 센서별 차이가 있는지 확인한다. |
| `range_m` | 개별 센서에서 표적까지의 거리 | 관측 거리와 거리 분포를 요약한다. |
| `azimuth_rad` | 개별 센서 기준의 방향 | 관측 방향과 속도의 관계를 계산한다. |
| `rcs_dbsm` | 레이더 반사 강도와 관련된 값 | 물체의 반사 특성을 평균·변동·분포로 요약한다. |
| `radial_velocity_mps` | 보정 전 방사 방향 속도 | 센서가 바라보는 방향의 속도 성분이다. |
| `radial_velocity_comp_mps` | 센서 이동 영향을 보정한 방사 방향 속도 | 표적 이동 정보를 추정하는 데 쓴다. |
| `x_m`, `y_m` | 공통 기준 좌표계의 위치 | 표적의 이동 궤적과 점들의 공간적 퍼짐을 계산한다. |
| `label` | 훈련 데이터의 정답 | 모델 학습과 검증에만 사용한다. |

여기서 방사 속도는 물체의 전체 이동 속도와 다르다. 예를 들어 센서 앞을 옆으로 지나가는 물체는 실제로 빠르게 움직여도 센서를 향해 가까워지거나 멀어지는 속도는 작을 수 있다. 따라서 **속도 열 하나의 평균만으로 분류하기에는 한계가 있다**고 보고 여러 방향의 관측과 위치 변화를 함께 활용했다.

또 `range_m`은 각 센서 기준이고 `x_m,y_m`은 공통 좌표계 기준이다. 센서마다 장착 위치와 방향이 다르므로 `range_m = sqrt(x_m² + y_m²)`라고 가정하면 안 됐다. 이 차이를 실제 데이터로 추정하는 것이 뒤의 개선 과정에 들어간다.

## 2. 데이터를 먼저 어떻게 확인했나

훈련·테스트 CSV를 읽고, 행 수·표적 수·결측값·표적별 정답 일관성을 확인했다. 다음 수치는 보존된 원본 CSV를 이번 문서 작성 시 다시 집계해서도 확인했다.

| 항목 | 확인값 |
| --- | --- |
| 훈련 CSV | 35,776행 × 11열 |
| 훈련 표적 | 1,000개 |
| 훈련 클래스별 표적 수 | 각각 200개 |
| 테스트 CSV | 10,729행 × 10열 |
| 테스트 표적 | 300개 |
| 결측값 | 훈련·테스트 모두 0개 |
| 훈련 표적 내부 정답 | 모든 표적에서 정답이 하나로 일치 |
| 센서 번호 | 1, 2, 3, 4 |

표적 하나의 관측량은 매우 달랐다.

| 훈련 표적당 항목 | 최소 | 중앙값 | 평균 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| detection 개수 | 3 | 18 | 35.776 | 513 |
| 서로 다른 관측 시점 수 | 2 | 9 | 9.486 | 26 |

이 차이는 중요한 단서였다. 어떤 표적은 점이 수백 개여서 모양과 움직임을 추정하기 쉽지만, 어떤 표적은 점 3개만으로 판단해야 한다. 같은 구조의 모델을 사용하더라도 정보량이 크게 달랐다.

훈련 데이터에서 클래스별 detection 개수의 중앙값은 대형 차량 72개, 일반 차량 24개, 이륜차 15개, 보행자 그룹 14.5개, 단독 보행자 9개였다. 이 결과는 **관측 개수 자체도 예측에 도움이 될 수 있다**는 단서다. 다만 개수만으로 정답을 결정하는 규칙은 만들지 않았다. 거리·방향·센서 조건도 관측 개수에 영향을 줄 수 있기 때문이다.

### 2.1 테스트를 60개씩 강제로 나누지 않았다

훈련 데이터는 클래스마다 200개로 균형이 맞았지만, 지문에는 테스트도 클래스마다 60개라는 조건이 없었다. 사용자는 제공한 자료가 전체라고 확인했다. 따라서 모델 예측을 강제로 클래스당 60개씩 재배분하지 않았다.

| `HEAVY_VEHICLE` | 58 |
| `LIGHT_VEHICLE` | 55 |
| `PERSONNEL` | 61 |
| `PERSONNEL_GROUP` | 72 |

## 3. 정답이 없는 테스트 대신, 어떻게 좋은 모델을 골랐나

### 3.1 같은 표적의 관측이 양쪽에 섞이지 않게 했다

35,776개의 detection 행을 무작위로 나누면 같은 표적의 일부 관측은 학습에, 나머지는 검증에 들어갈 수 있다. 그러면 이미 본 표적과 매우 비슷한 관측으로 성능을 측정하게 된다.

이를 피하려고 먼저 `sample_id`별 특징을 만들었다. 그 결과 학습표의 행 수는 **1,000행**이 된다. 이 1,000개 표적을 분할하므로 같은 표적이 학습과 검증에 동시에 들어가지 않는다.

### 3.2 5분할 교차검증과 OOF

기본 분할은 `StratifiedKFold(5, shuffle=True, random_state=42)`였다. 클래스 비율을 유지하면서 1,000개 표적을 다섯 묶음으로 나눈다.

```text
1회: 800개로 학습 → 남은 200개 예측
2회: 다른 800개로 학습 → 다른 200개 예측
...
5회: 나머지 조합으로 학습 → 마지막 200개 예측

각 표적이 자신을 학습에 넣지 않은 모델에게 예측을 한 번씩 받는다.
그 예측 1,000개를 모아 정확도를 계산한다.
```

이렇게 모은 예측을 **OOF(out-of-fold) 예측**이라고 한다. 정확도 89.3%는 이 1,000개의 OOF 예측에서 나온 수치다.

5개 fold는 각각 학습 데이터의 다른 부분을 본 모델이기도 하다. 테스트 예측에서는 보통 이 5개 모델의 **클래스별 확률을 평균**했다.

### 3.3 미세조정에서는 조기 종료용 검증을 한 번 더 분리했다

신경망은 학습을 오래 한다고 계속 좋아지지 않는다. 어느 시점부터 훈련 데이터에 지나치게 맞출 수 있으므로, 별도 데이터의 성능을 보며 학습을 멈추는 **조기 종료(early stopping)**를 쓴다.

최종 TabICL 미세조정에서는 바깥 검증 200개의 정답을 조기 종료에 쓰지 않았다. 각 fold의 학습용 800개 안에서 다시 15%를 내부 검증용으로 나누도록 설정했다. 개수로 이해하면 대략 **680개는 미세조정, 120개는 조기 종료 판단, 바깥 200개는 OOF 평가**의 역할을 갖는다. 내부의 구체적인 학습 묶음 구성은 TabICL 라이브러리가 처리한다.

이 구조 덕분에 바깥 검증 정답을 보고 그 fold의 최적 학습 시점을 고르는 문제를 피했다. 관련 코드에도 바깥 검증 정답을 학습·조기 종료에 쓰지 않는다는 설명이 들어 있다.

다만 **모델 종류·특징·가중치를 고르는 데는 개발 OOF 점수를 여러 번 사용했다.** 따라서 89.3%는 완전히 손대지 않은 독립 시험 점수가 아니다. 분할 seed를 123, 2026으로 바꾼 반복 검증도 실시했지만, 이것도 같은 훈련 데이터의 재분할이다.

## 4. 첫 시도: 통계 특징과 트리 모델

### 4.1 레이더 관측 묶음을 숫자 한 줄로 바꿨다

가장 먼저 만든 `radar_features()`는 표적별로 **78개의 기본 특징**을 계산한다.

| 특징 묶음 | 개수 | 의미 |
| --- | ---: | --- |
| 관측량 | 3 | 전체 detection 수, 서로 다른 시점 수, 센서 수 |
| 기본 분포 통계 | 49 | 7개 측정값 각각의 평균·표준편차·최소·최대·10% 분위수·중앙값·90% 분위수 |
| 시간 변화와 잔차 | 12 | x·y·RCS·보정 속도의 시간 기울기, 직선 추세를 뺀 잔차의 표준편차·분위수 폭 |
| 공간 형상 | 2 | 이동 추세를 뺀 x·y 점들의 공분산 고유값 |
| 궤적 속력·보정 속도 크기 | 2 | x·y 변화율의 크기, 보정 방사 속도 절댓값의 평균 |
| 시점별 관측 개수 | 2 | 한 시점에 잡힌 점 개수의 평균·표준편차 |
| 같은 시점 내부의 퍼짐 | 4 | x·y·RCS·보정 속도가 동일 시점 안에서 얼마나 퍼지는지 |
| 센서별 관측 비율 | 4 | 1~4번 센서가 전체 점에서 차지하는 비율 |
| 합계 | **78** | 표적 하나를 나타내는 수치 특징 |

평균은 전반적인 수준을, 표준편차는 흔들림을, 분위수는 극단값에 덜 휘둘리는 분포의 범위를 알려준다. 예를 들어 RCS 평균이 비슷하더라도, 반사 강도의 변동이나 점들의 공간적 퍼짐이 다르면 서로 다른 표적일 수 있다.

시간 변화는 다음과 같은 직선으로 요약했다.

```text
x 위치 ≈ 평균 x + x 변화율 × 중심화한 시간
y 위치 ≈ 평균 y + y 변화율 × 중심화한 시간
```

직선을 뺀 나머지를 **잔차**라고 부른다. 점 전체가 이동해서 넓게 퍼진 것과 표적 자체의 폭 때문에 퍼진 것을 어느 정도 분리하려는 방법이다. 잔차 점들이 길쭉하게 퍼지는지, 두 방향으로 넓게 퍼지는지를 고유값 두 개로 요약했다. 고유값의 제곱근은 각 주축 방향의 퍼짐 규모로 이해할 수 있다.

### 4.2 최초 ExtraTrees: 84.9%

첫 기준 모델은 ExtraTrees였다. 여러 결정나무가 서로 다른 기준으로 표적을 분류하고 결과를 모으는 방식이다.

실제 설정은 다음과 같다.

| 항목 | 값 |
| --- | --- |
| 나무 개수 | 400 |
| `max_features` | 0.8 |
| 난수 seed | 42 |
| 검증 | 표적 단위 5분할, 분할 seed 42 |
| 입력 | 기본 특징 78개 |
| OOF 정확도 | **84.9%** |

이 단계에서 테스트 300개의 유효 CSV를 먼저 확보했다. 이후 실험이 실패하더라도 제출 가능한 결과를 보존할 수 있었다.

### 4.3 GPU CatBoost로 바꿨지만 점수가 낮았다

다음에는 GPU에서 CatBoost를 돌렸다. 나무의 깊이를 바꿔 비교했다.

| 설정 | OOF 정확도 |
| --- | ---: |
| CatBoost 깊이 3 | 82.8% |
| CatBoost 깊이 4 | 83.1% |
| CatBoost 깊이 6 | 83.3% |

공통으로 1,200회 반복, 학습률 0.035, `l2_leaf_reg=5`, seed 42를 사용했다. **GPU를 썼다는 사실만으로 더 좋은 모델이 되지는 않았다.** 관측 묶음을 표현하는 방식과 소규모 데이터에 맞는 모델을 함께 바꿔야 했다.

초기 하네스도 점수가 높은 ExtraTrees를 선택했다. 당시 `competition-runs/.../selected.json`의 84.9% 후보는 **초기 선택 기록**이며, 이후 만들어진 최종 89.3% 후보와 다르다.

## 5. 두 번째 시도: 센서 좌표와 물리적 의미를 반영했다

### 5.1 센서별 좌표 변환을 데이터에서 추정했다

개별 센서의 극좌표를 먼저 평면 좌표로 바꾼다.

```text
센서 기준 x = range_m × cos(azimuth_rad)
센서 기준 y = range_m × sin(azimuth_rad)
```

이 좌표와 이미 제공된 공통 좌표 `x_m,y_m` 사이의 변환을 센서별 최소제곱으로 추정했다. 쉽게 말해 **센서마다 얼마나 돌아가 있고 어디에 달려 있는지 데이터의 대응 관계로 맞췄다.**

계산한 변환에는 회전 부분과 이동 부분이 있다. 저장된 이동 부분을 예로 들면 1번 센서는 약 `(3.663, -0.873)`, 4번 센서는 약 `(3.663, 0.873)`이었다. 이는 데이터 내부 좌표 변환의 추정값이며, 실제 장비를 측량한 값이라는 뜻은 아니다.

이 계산에는 정답 `label`을 사용하지 않았다. 다만 센서 변환은 훈련 데이터 전체의 좌표로 한 번 추정해 고정했으므로, 전체 전처리를 fold 안에서 매번 다시 추정한 엄격한 검증과는 차이가 있다. 변환이 고정된 좌표 관계를 복원하는 역할이었다는 점과 함께 기록할 필요가 있다.

### 5.2 방사 속도 여러 개로 평면 속도를 추정했다

센서마다 공통 좌표계에서 어느 방향을 바라보는지 알면, 방사 속도는 대략 다음 식으로 표현할 수 있다.

```text
관측한 방사 속도 ≈ 관측 방향의 x 성분 × vx
                    + 관측 방향의 y 성분 × vy
```

여러 detection을 함께 사용해 `vx,vy`를 맞추고, 그 크기를 `doppler_speed`라는 특징으로 만들었다. 방향이 비슷한 관측만 있으면 추정이 불안정할 수 있으므로, 안정화 항을 추가한 ridge 추정과 위치·도플러를 함께 맞추는 추정도 비교했다.

중요한 점은 이 값을 ‘복원한 정확한 실제 속도’로 확정하지 않았다는 것이다. 관측 오차와 센서 움직임이 남을 수 있으므로 **분류기에 제공할 추정 특징**으로 사용했다.

### 5.3 모양과 분포를 더 자세히 표현했다

기본 특징에 다음 정보를 추가했다.

- 이동을 빼기 전, 시간 궤적을 뺀 뒤, 도플러 추정 이동을 뺀 뒤의 공간 형상
- 주축 방향의 퍼짐, 분위수 폭, 면적과 길쭉한 정도
- 같은 시점 내부의 공분산
- RCS와 속도 분포의 비대칭·꼬리 정도, 사분위 범위와 중앙값 절대편차
- 속도 추정의 잔차와 관측 방향의 불안정성

이렇게 기본 78개에 추가 87개를 더해 **165개 특징**을 만들었다.

### 5.4 `original 79`라는 이름에 숨어 있는 세부사항

실험 코드에서는 확장 특징표의 앞 79개를 잘라 `original`이라고 불렀다. 실제 열을 확인하면 다음과 같다.

```text
기본 집계 특징: 78개
original:      기본 78개 + 첫 추가 특징 doppler_speed = 79개
all:           기본 78개 + 추가 87개 = 165개
```

따라서 최종 모델의 `original 79`는 **완전히 최초의 기본 특징만 사용한 모델이 아니다.** 도플러 속력 추정값 하나가 포함된다. 실험 이름을 그대로 읽을 때 놓치기 쉬운 부분이다.

또 `features_initial.csv`는 78개 특징에 정답 `label`을 붙여 둔 분석용 파일이다. 열이 79개라고 해서 모두 입력 특징인 것은 아니다. 실제 초기 모델은 `radar_features()`의 출력으로, 최종 모델은 정답이 없는 특징표와 별도 `labels.csv`로 학습했다.

근거: [좌표·추가 특징 코드](race90/custom_adapters/radar_improved.py), [센서 변환 추정값](race90/competition/q1/sensor_geometry.json), [165개 훈련 특징표](race90/competition/q1/features_improved.csv).

## 6. 세 번째 시도: 사전학습 표형 모델 TabICL

### 6.1 TabICL을 쉽게 이해하기

표형 데이터는 ‘표적 하나가 한 행이고 특징들이 여러 열인 표’를 말한다. TabICL은 이런 표형 분류를 위해 사전학습된 신경망이다.

일반적인 트리 모델은 대회 데이터로 분기 규칙을 새로 만든다. TabICL은 사전학습된 능력을 가진 상태에서 **정답이 있는 행들을 참고 자료로 함께 보고, 정답 없는 행의 클래스를 예측**한다. 여기서 참고 자료를 **문맥(context)**이라고 부른다.

`TabICLClassifier.fit()`으로 참고할 특징·정답을 지정하는 것과, 뒤에서 수행한 **미세조정으로 신경망 가중치를 실제로 바꾸는 것**은 구별해야 한다. 첫 TabICL 실험은 사전학습 모델을 그대로 사용한 문맥 기반 분류였고, 최종 모델에는 추가 미세조정이 들어갔다.

당시 실행 기록에서 사용된 기본 사전학습 체크포인트 이름은 `tabicl-classifier-v2-20260212.ckpt`였다. 최종 학습 코드도 이 기본값을 별도로 바꾸지 않았다.

### 6.2 단독보다 두 특징 조합을 평균했을 때 좋았다

처음에는 내부 추론 앙상블 크기를 16으로 두고 비교했다.

| 후보 | 입력 | OOF 정확도 |
| --- | --- | ---: |
| TabICL `original` | 79개 | 86.9% |
| TabICL `all` | 165개 | 86.4% |
| 두 후보의 예측 확률을 50:50 평균 | 79개 + 165개 | **87.3%** |

165개 모델이 단독으로 더 낮아도 앙상블에 도움이 됐다. 두 모델이 틀리는 표적이 완전히 같지는 않았기 때문이다. 앙상블은 각 모델이 고른 정답을 단순 투표하기보다 **5개 클래스 각각의 확률을 평균한 뒤 가장 큰 클래스를 고르는 방식**이었다.

예를 들어 두 모델의 차량/대형 차량 확률이 각각 `(0.6,0.4)`, `(0.3,0.7)`이면 평균은 `(0.45,0.55)`다. 모델이 얼마나 확신하는지도 평균에 반영된다. 이 숫자는 설명용 예시이며 실제 특정 표적의 출력은 아니다.

### 6.3 전통적인 모델도 넓게 탐색했다

같은 시기 RBF SVM, QDA, Gaussian Naive Bayes, ExtraTrees, RandomForest를 비교하는 탐색 코드도 실행했다. 전체 특징뿐 아니라 물리적 의미가 있는 작은 특징 집합, 부호를 유지하는 로그 변환, 규제 강도 등을 조합했다. 코드에 정의된 설정은 202개였다.

실행 로그의 최상위 결과는 전체 165개 특징을 사용하는 ExtraTrees 설정으로 **84.1%**였다. 이 탐색의 최상위도 당시 TabICL 87.3% 앙상블보다 낮아 최종 선택으로 이어지지 않았다. 202개 설정 모두의 원본 결과표가 현재 작업 폴더에 남아 있지는 않으므로, 없는 개별 점수를 만들어 채우지는 않았다.

근거: [최초 TabICL 비교 코드](race90/scripts/radar_tabicl.py), [전통 모델 탐색 코드](race90/scripts/radar_model_search.py), 당시 대화·도구 실행 기록의 05:18·05:21~05:24 UTC 결과.

## 7. 특징을 더 만들거나 줄여 본 시행착오

여기부터의 실험은 여러 GPU 작업으로 일부 겹쳐 진행됐다. 아래 순서는 이해하기 쉽도록 접근법별로 묶은 것이다. 정확한 실행 순서를 전부 분 단위로 복원했다는 뜻은 아니다.

### 7.1 튀는 점의 영향을 줄이는 robust 특징

레이더 점 중 일부가 멀리 튀면 평범한 평균과 분산이 크게 변할 수 있다. 이를 줄이려고 궤적을 반복해서 맞추면서 멀리 떨어진 점의 가중치를 낮추고, 잔차가 작은 60%·80%·90%·전체 점에서 각각 모양을 계산했다. 속도와 RCS의 분위수, 가운데 구간만 쓴 평균·표준편차도 추가했다.

165개에 50개를 추가한 특징표가 **215개 robust 특징표**다.

| 후보 | OOF 정확도 | 판단 |
| --- | ---: | --- |
| 215개 전체를 쓴 TabICL `robust_all` | 86.9% | 기존 두 모델 조합을 대체하지 않음 |
| 앞 79개 + robust 추가분 `robust_base` | 86.6% | 단독 개선 없음 |
| robust 표의 전체 215개를 쓴 ExtraTrees | 83.6% | 성능 하락 |
| 앞 79개를 쓴 해당 ExtraTrees 비교 | 84.1% | 최종 후보보다 낮음 |

robust 처리가 항상 유리하지는 않았다. 극단값 중에는 측정 잡음도 있지만 표적 종류를 구분하는 신호도 있을 수 있다. 이 설명은 결과에 대한 가능한 해석이며 원인을 분리해 입증한 실험 결과는 아니다.

### 7.2 센서 이동과 회전의 영향을 분리하는 physics 특징

보정 속도에서 원시 속도를 뺀 차이를 이용해 센서 쪽 움직임을 추정했다. 여기에 센서 장착 위치를 이용한 회전 효과, 위치 궤적과 도플러를 결합한 속도, 진행 방향과 옆 방향의 퍼짐, 센서별 관측 통계, 시점별 점 개수·간격 등을 추가했다.

추가분은 122개였고, 앞의 215개에 붙여 총 **337개**가 됐다.

| 후보 | OOF 정확도 |
| --- | ---: |
| 337개 전체 | 85.7% |
| 앞 79개 + physics 추가분 | 85.7% |
| 축약 특징 + physics 추가분 | 84.6% |

물리적으로 더 정교한 특징을 넣었지만 기존 앙상블을 넘지 못했다. 여기서도 실제 관측의 보정 방식이 추정식과 정확히 맞는지, 추가 특징이 중복되거나 불안정한지 등 여러 가능성이 남았다. **물리 지식으로 만든 특징이라는 이유만으로 채택하지 않고 점수로 비교했다.**

### 7.3 위치·방향 관련 특징을 빼 보았다

위치와 방향이 우연한 상관관계일 가능성을 생각해, 거리·방향·절대 위치 등의 일부 특징을 제거한 작은 집합을 만들었다.

| 후보 | OOF 정확도 |
| --- | ---: |
| `compact` | 85.8% |
| `compact_robust` | 84.9% |
| `compact_no_direction` | 85.0% |

특징을 줄인 모델도 단독으로 기존 앙상블보다 낮았다. 거리·방향 정보가 이 데이터에서 도움이 됐다는 결과이지만, 다른 장소·센서로 일반화된다는 증거까지 얻은 것은 아니다.

### 7.4 중요도가 높은 특징만 남겨 보았다

각 fold의 학습 부분에서 ExtraTrees로 특징 중요도를 계산하고 상위 특징만 TabICL에 넣었다. 검증 정답으로 특징을 골라 넣지는 않았다.

| 선택한 특징 수 | 12 | 20 | 32 | 48 | 64 | 96 | 160 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| OOF 정확도 | 80.4% | 81.5% | 82.1% | 82.9% | 83.3% | 84.7% | 85.3% |

이 경우에는 강하게 줄일수록 손실이 컸다. 개별 특징 중요도가 낮아도 여러 특징을 조합할 때 쓰이는 정보가 있었을 가능성이 있다.

센서 이동 특징을 조금만 추가하거나 이상치 처리 임계값·모델 seed를 바꾸는 비교도 진행했다. 단독 결과는 대체로 85~86%대였다. 당시 일부 소량 혼합에서 87.5~87.6%가 나오기도 했지만, 이후 미세조정 모델이 더 좋은 결과를 냈다.

### 7.5 센서별 차이를 먼저 제거하는 특징

각 센서가 관측한 점들이 일정하게 어긋나 있으면, 그 차이가 표적의 폭처럼 보일 수 있다. 이를 줄이려고 **센서별 절편 + 공통 시간 기울기**를 가진 모형으로 위치를 맞췄다. RCS와 속도에서도 센서별 평균 차이를 분리하고, 반사가 강한 점에 가중치를 준 모양도 만들었다.

별도 센서 특징은 104개였다. 전부 넣는 대신 8개 핵심 특징만 추가하는 비교도 했다.

| 후보 | OOF 정확도 |
| --- | ---: |
| 앞 79개 + 센서 특징 전체 | 86.0% |
| 165개 + 센서 특징 전체 | 86.4% |
| 앞 79개 + 센서 형상·RCS 일부 | 86.5% |
| 앞 79개 + 센서 특징 8개 | **87.2%** |
| 앞 79개 + 센서 특징 + physics 추가분 | 86.1% |

적은 특징만 추가한 쪽이 가장 좋았지만, 최종 미세조정 앙상블을 넘지는 못했다.

### 7.6 한 덩어리인지 여러 덩어리인지 보는 군집 특징

특히 보행자 한 명과 여러 명의 그룹을 구분하려면 평균과 분산만으로 부족할 수 있다. 그래서 점들 사이의 거리, 가장 가까운 이웃의 거리, 최소 신장 트리의 연결 길이, DBSCAN 군집 수와 잡음 비율, 2~3개 덩어리로 나눴을 때의 설명력 등을 계산했다.

원래 위치, 이동을 뺀 위치, 센서별 차이를 뺀 위치, RCS·속도 공간에서 계산한 군집 특징은 총 131개였다. 점이 많은 표적은 계산량을 줄이기 위해 최대 128개 점을 선택했다.

| 특징 조합 | TabICL OOF | LightGBM OOF |
| --- | ---: | ---: |
| 앞 79개 + 군집 특징 전체 | 84.7% | 83.7% |
| 앞 79개 + 센서 보정 군집 특징 | 86.0% | 85.2% |
| 앞 79개 + RCS·속도 군집 특징 | 86.2% | 83.7% |
| 165개 + 군집 특징 전체 | 85.6% | 완성된 결과 파일 없음 |

이 접근도 최종 후보로 채택하지 않았다. 표의 ‘완성된 결과 파일 없음’은 해당 설정의 실행 성공이나 점수를 확인할 자료가 없다는 뜻이다.

근거: [robust 특징](race90/scripts/radar_robust.py), [physics 특징](race90/scripts/radar_physics.py), [특징 선택](race90/scripts/radar_feature_search.py), [센서 특징](race90/scripts/radar_sensor_features.py), [군집 특징](race90/scripts/radar_cluster_features.py). 개별 결과는 부록 A에 있다.

## 8. 다른 모델과 학습 방식도 시험했다

### 8.1 원시 점군을 직접 학습한 PointNet 계열

통계로 요약하는 과정에서 중요한 정보가 사라질 수 있다는 생각으로, 각 detection을 직접 신경망에 넣는 방식도 만들었다.

점 하나를 다음 정보가 포함된 15차원 벡터로 표현했다.

- 중심화한 시간
- 중심화한 x·y 위치와 직선 이동을 뺀 위치 잔차
- RCS, 원시 속도, 보정 속도, 두 속도의 차이
- 공통 좌표계의 관측 방향 두 성분
- 센서 번호를 나타내는 4개 표시값

표적별 점 개수가 다르므로 빈칸을 채워 길이를 맞추고, 진짜 점만 계산하도록 마스크를 사용했다. 최대 256개 점을 사용했고, 점들을 신경망으로 변환한 뒤 평균·표준편차·최댓값·학습한 가중평균을 계산했다. 이 결과를 337개 통계 특징의 신경망 표현과 합쳐 분류했다.

학습에는 AdamW, 학습률 0.0015, weight decay 0.02, 최대 160 epoch, cosine 학습률 감소, 작은 잡음 추가, label smoothing 0.03을 사용하도록 작성했다.

| 모델 seed | OOF 정확도 |
| --- | ---: |
| 42 | 80.7% |
| 123 | 80.0% |
| 2026 | 78.8% |

이 초기 PointNet 코드는 바깥 검증의 log loss가 가장 좋은 epoch를 선택한다. 따라서 **해당 OOF는 최종 TabICL의 내부 검증 분리 방식보다 낙관적일 수 있다.** 그 조건에서도 성능이 낮아 최종 후보로 선택되지 않았다.

### 8.2 점들 사이의 관계를 보는 Set Transformer

점마다 독립적으로 계산하는 데서 더 나아가, attention으로 점들이 서로를 보게 하는 모델도 만들었다. 최대 128개 점, 64차원 표현, 4개 attention head를 가진 2개 층과 앞 79개 특징을 결합했다.

이 모델은 내부 검증으로 학습 epoch 수를 고른 뒤, 바깥 학습 데이터 전체에서 새 모델을 학습하는 방식으로 검증 절차를 개선했다. 결과는 **79.1%**였다.

원시 점을 직접 쓰는 접근은 최종 모델보다 낮았다. 훈련 표적이 1,000개라는 규모에서 처음부터 학습한 모델이 충분한 분류 패턴을 익히기 어려웠을 가능성이 있지만, 데이터 수만이 원인이라고 검증한 것은 아니다.

### 8.3 다른 표형 데이터 신경망·사전학습 모델

| 모델 | 시험한 방식 | 주요 OOF 결과 | 결정 |
| --- | --- | --- | --- |
| TabPFN v2 | 사전학습 모델, 79·165·215개 특징 | 86.0% / 85.6% / 85.0% | 당시 TabICL 조합보다 낮음 |
| TabPFN v2 미세조정 | 앞 79개, 학습률 1e-5, 최대 50 epoch | 87.0% | 최종 TabICL보다 낮음 |
| TabDPT | 기본·robust·분위수 정규화, 특징 수 변경 | 79.5~84.7% | 채택하지 않음 |
| TabM | 수치 임베딩과 16개 내부 멤버를 갖는 MLP 계열 | 79개 82.7%, 165개 80.9%, 337개 80.4% | 채택하지 않음 |
| Mitra | 사전학습 그대로와 미세조정 비교 | 그대로 83.7~84.3%, 미세조정 84.6~85.0% | 채택하지 않음 |

TabDPT는 표준화뿐 아니라 robust 정규화, 분위수 기반 정규화를 바꾸어 보았다. 79개 특징에서는 세 방식 모두 84.7%였고, 특징을 많이 붙인 쪽은 더 낮았다.

TabM은 내부 검증으로 epoch 수를 선택하고 바깥 학습 데이터로 새로 학습했다. Mitra는 별도 실행 환경을 준비해 기존 학습 환경과 충돌을 줄였다. 모델 이름만 늘린 것이 아니라 입력 표현과 학습 여부도 함께 비교했다.

### 8.4 실제로 발생한 구현 문제: TabPFN의 `classes_`

TabPFN 미세조정 실행 중 `FinetunedTabPFNClassifier`에 일반적인 sklearn 방식의 `classes_` 속성이 없어 오류가 발생했다. 같은 분할에 5개 클래스가 모두 존재하고 내부 라벨 인코더가 정렬된 클래스를 사용하는 점을 확인한 뒤, 결과 클래스 순서를 `np.unique(y)`로 명시하도록 수정했다.

수정 후 완성된 5분할 결과는 87.0%였다. API 차이를 처리해 실험은 마쳤지만 최종 모델로 채택되지는 않았다. 다른 문제의 이미지 학습 오류는 이 문서의 범위에 포함하지 않았다.

### 8.5 자주 헷갈리는 두 클래스만 전문적으로 구분하기

전체 5개를 한 번에 맞히는 대신, 보행자/그룹이나 일반 차량/대형 차량처럼 헷갈리는 쌍만 분류하는 **이진 전문 모델**도 시험했다.

사전학습 TabICL 전문 모델은 5개 클래스 쌍과 4개 특징 구성을 비교했다. 그중 보행자/그룹 쌍에서의 정확도는 83.0~84.25%였다. 다른 클래스 쌍의 높은 이진 정확도는 두 클래스만 골라 평가한 값이므로 5클래스 전체 정확도와 직접 비교하면 안 된다.

후반에는 보행자/그룹 전용 TabICL을 별도로 미세조정했다.

| 비교 항목 | 결과 |
| --- | ---: |
| 새 전문 모델의 보행자/그룹 이진 정확도 | 84.75% |
| 기존 최종 계열 모델에서 두 클래스 확률만 비교한 정확도 | 86.5% |
| 시험한 혼합 중 가장 높은 5클래스 전체 정확도 | 88.9% |

오히려 기존 모델이 두 클래스를 더 잘 구분했다. 전문 모델은 최종 89.3% 조합에 넣지 않았다.

### 8.6 관측점이 적은 표적에 비슷한 참고 사례만 보여주기

관측점이 적으면 분류가 어렵다는 분석을 바탕으로, TabICL의 참고 문맥을 관측점 개수가 비슷한 훈련 표적으로 제한했다. 개수 구간을 겹치게 나누는 방식과 넓게 나누는 방식을 비교했다.

두 방식 모두 OOF **88.3%**였다. 여기에는 이미 미세조정한 체크포인트를 사용했다. 원시 모델과 특징만 바꾼 실험과는 조건이 다르다. 최종적으로 전체 훈련 문맥을 사용하는 앙상블보다 낮아 채택하지 않았다.

### 8.7 확신도 높은 예측을 의사 라벨로 사용하기

기존 모델이 확률 95% 또는 99% 이상으로 확신하는 표적의 예측을 임시 정답처럼 취급했다. 그 표적들을 추가 참고 문맥에 넣어, 애매한 나머지 표적을 다시 예측했다. 이것이 **의사 라벨(pseudo-label)** 실험이다.

바깥 검증에서는 검증 표적의 실제 정답을 문맥에 넣지 않았다. 대신 해당 검증 묶음의 특징과 모델이 만든 임시 정답을 사용했다. 이런 방식은 정답 없는 대상들을 함께 활용하는 방식이므로 일반적인 독립 행 추론과 조건이 다르다.

| 구성 | 분할 seed 42 | 분할 seed 2026 |
| --- | ---: | ---: |
| 당시 기준인 128 추론 조합 | 89.0% | 88.6% |
| 확신도 95% 이상 추가 | 89.1% | 88.6% |
| 확신도 99% 이상 추가 | 89.1% | 88.5% |

첫 분할에서는 1개 더 맞혔지만 두 번째 분할에서 개선이 반복되지 않았다. 잘못된 확신을 참고 자료에 추가할 수 있고 절차도 복잡해지므로 채택하지 않았다.

근거: [PointNet](race90/scripts/radar_pointnet.py), [Set Transformer](race90/scripts/radar_set_transformer.py), [TabPFN 미세조정](race90/scripts/radar_tabpfn_finetune.py), [전문 모델](race90/scripts/radar_specialists.py), [이진 미세조정](race90/scripts/radar_binary_finetune.py), [문맥 제한](race90/scripts/radar_local_context.py), [의사 라벨](race90/scripts/radar_pseudolabel.py), [추가 실험 판단 기록](race90/competition/q1/additional_experiments.json).

## 9. 성능을 가장 많이 끌어올린 변화: TabICL 미세조정

### 9.1 기존 능력을 대회 데이터에 맞게 조금씩 바꿨다

첫 TabICL은 사전학습 가중치를 그대로 사용했다. 미세조정에서는 대회 훈련 데이터로 신경망의 가중치를 실제로 업데이트했다.

TabICL은 정답이 있는 참고 행과 예측할 행을 함께 다루는 구조다. 미세조정도 훈련 데이터 안에서 이런 참고·예측 구성을 만들며 이루어진다. 학습 손실은 정답 클래스의 확률을 높이도록 하는 **교차엔트로피(cross entropy)**이고, 저장할 최적 시점은 내부 검증의 log loss로 판단했다. 전체 사전학습을 새로 한 것이 아니라 **이미 학습된 모델을 작은 학습률로 적응시킨 전이학습**이다.

먼저 학습률 `1e-5`, 최대 60 epoch를 시험했다.

| 특징 | 분할 seed | OOF 정확도 |
| --- | ---: | ---: |
| original 79 | 42 | 87.6% |
| all 165 | 42 | 87.5% |
| original 79 | 123 | 87.5% |
| original 79 | 2026 | 87.5% |
| all 165 | 2026 | 87.7% |

이후 학습률을 `3e-5`로 높이고 최대 학습 횟수를 늘렸다.

| 특징 | 최대 epoch | 분할 seed | OOF 정확도 |
| --- | ---: | ---: | ---: |
| original 79 | 120 | 42 | **88.4%** |
| all 165 | 100 | 42 | **87.8%** |
| original 79 | 120 | 2026 | 88.1% |
| all 165 | 100 | 2026 | 87.1% |

여기서 epoch는 설정한 최대치다. 조기 종료를 사용했으므로 모든 fold가 반드시 120회·100회 끝까지 학습한 것은 아니다. 현재 요약 JSON만으로 각 fold의 실제 최적 epoch를 전부 확정할 수는 없다.

### 9.2 최종 채택된 두 모델의 정확한 설정

| 항목 | original 모델 | all 모델 |
| --- | --- | --- |
| 입력 특징 수 | 79 | 165 |
| 모델 | `FinetunedTabICLClassifier` | 동일 |
| 사전학습 체크포인트 | `tabicl-classifier-v2-20260212.ckpt` 기본값 | 동일 |
| 학습률 | `3e-5` | `3e-5` |
| 최대 epoch | 120 | 100 |
| 바깥 교차검증 | 5분할, 계층화, seed 42 | 동일 |
| 모델 seed | 42 | 42 |
| 내부 검증 비율 | 0.15 | 0.15 |
| 조기 종료 기준 | log loss | log loss |
| 개선이 없을 때 기다리는 epoch 수 | 20 | 12 |
| 미세조정 중 내부 앙상블 크기 | 4 | 4 |
| 내부 검증 때 앙상블 크기 | 8 | 8 |
| 최초 추론 앙상블 크기 | 32 | 32 |
| 열·행 처리 모듈 동결 | 둘 다 하지 않음 | 동일 |
| 저장 | fold별 `best.ckpt` | 동일 |
| 학습 장치 기록 | `cuda:0` | `cuda:2` |
| 5개 fold 처리 시간 기록 | 약 399초 | 약 512초 |

시간에는 해당 실행의 학습·평가 등 코드 구간이 포함되며, 여러 작업이 동시에 실행되던 당시 환경의 측정값이다. 두 시간을 더해서 대회 전체 소요 시간으로 해석하면 안 된다.

최종 JSON에는 일부 기본 인자가 생략되어 있다. 학습 코드와 당시 설치된 API의 시그니처 확인 기록을 대조하면, 별도로 바꾸지 않은 설정은 **AdamW, weight decay 0.01, gradient clipping 1.0, AMP 활성화, warmup 비율 0.1을 사용하는 학습률 스케줄 활성화**였다. 이 값들은 별도 탐색으로 선택한 값이 아니라 당시 라이브러리 기본값을 사용한 것이다.

### 9.3 학습 설정을 더 크게 한다고 늘 좋아지지는 않았다

다음 변경도 비교했다.

| 변경 | 결과 | 결정 |
| --- | ---: | --- |
| 미세조정 내부 앙상블 16, 내부 검증 앙상블 32 | 87.4% | 채택하지 않음 |
| 열 처리 모듈을 고정하고 나머지만 학습 | 86.8% | 채택하지 않음 |
| 모델 seed를 123으로 바꾼 original | 87.3% | 비교용 보존 |
| 모델 seed를 123으로 바꾼 all | 87.8% | 동일 가중치 추가에서 개선 없어 제외 |

단순히 계산을 늘리거나 학습 가능한 부분을 줄이는 것보다, 이 데이터에서 실제 성능을 확인하며 설정을 고르는 것이 중요했다.

## 10. 최종 앙상블은 정확히 어떻게 만들었나

### 10.1 먼저 네 미세조정 설정을 합쳐 88.8%

중간 후보는 다음 네 설정의 확률을 각각 25%씩 평균했다.

1. original 79, 학습률 1e-5
2. all 165, 학습률 1e-5
3. original 79, 학습률 3e-5
4. all 165, 학습률 3e-5

개발 OOF는 **88.8%**였다. 당시의 `finetune_ensemble.npz`와 `submission.finetuned.csv`에 해당하는 중간 후보다.

### 10.2 좋은 두 설정의 추론 앙상블을 128로 늘려 89.0%

이후 학습률 3e-5의 original·all 두 설정을 사용하고, 추론 시 내부 앙상블 크기를 32에서 128로 늘렸다. 두 특징 구성의 확률을 50:50 평균했을 때 **89.0%**였다.

여기서 `n_estimators=128`은 **신경망 128개를 별도로 미세조정했다는 뜻이 아니다.** 같은 신경망 가중치에 대해 특징·클래스 순서와 전처리 구성 등을 달리하는 내부 추론 앙상블의 크기다. 이것은 5개 fold 모델을 평균하는 것과도 다른 층위의 앙상블이다.

### 10.3 테스트에서는 훈련 표적 1,000개를 모두 참고 문맥으로 사용

OOF 평가 때는 검증 정답이 새어 들어가지 않도록 해당 fold의 학습 표적 800개만 참고 문맥으로 사용했다.

테스트는 정답 없는 별도 300개이므로, 이미 저장한 fold별 가중치를 불러온 뒤 훈련 1,000개의 특징·정답을 전부 참고 문맥으로 제공했다. 이때 `TabICLClassifier.fit(X, y)`는 **문맥을 바꾸는 단계**이며, 1,000개 전체로 가중치 미세조정을 다시 한 단계가 아니다.

각 재추론 파일에는 두 종류의 테스트 확률이 들어 있다.

| 배열 이름 | 의미 |
| --- | --- |
| `test` | 각 fold의 학습 800개 문맥으로 예측한 테스트 확률을 5개 fold 평균 |
| `test_full` | 각 fold의 저장 가중치에 훈련 1,000개 전체 문맥을 제공한 테스트 확률을 5개 fold 평균 |

최종 Notebook에 저장한 것은 **`test_full`**이다. 배열 이름을 구분하지 않고 `test`를 가져오면 최종 제출과 다른 결과가 될 수 있다.

### 10.4 128과 512 추론을 함께 평균해 89.3%

마지막에는 같은 두 학습 설정을 내부 추론 앙상블 512로도 재실행했다.

| 저장된 예측 구성 | OOF 정확도 | 최종 가중치 |
| --- | ---: | ---: |
| original 79, 추론 128 | 88.5% | 25% |
| original 79, 추론 512 | 88.4% | 25% |
| all 165, 추론 128 | 87.9% | 25% |
| all 165, 추론 512 | 88.1% | 25% |
| 위 네 확률의 평균 | **89.3%** | 합계 100% |

original 단독은 512에서 약간 낮아졌다. 그럼에도 네 출력을 평균한 조합은 더 좋았다. **내부 추론을 많이 돌릴수록 무조건 좋아지는 관계는 아니었고**, 다른 출력 간의 보완 효과가 최종 선택에 작용했다.

최종 공식을 쓰면 다음과 같다.

```text
P(표적의 클래스) = 0.25 × P(original, 128)
                  + 0.25 × P(original, 512)
                  + 0.25 × P(all, 128)
                  + 0.25 × P(all, 512)

각 P의 테스트 확률 = 저장된 5개 fold 가중치의 예측 평균
각 fold의 테스트 참고 문맥 = 훈련 표적 1,000개 전체
최종 label = 5개 클래스 중 평균 확률이 가장 큰 클래스
```

**독립적으로 미세조정한 최종 가중치는 2개 특징 구성 × 5개 fold = 총 10개다.** 128과 512는 이 10개 가중치를 다시 사용한 재추론이다. 네 확률 파일이 있다고 해서 서로 다른 가중치 20개를 새로 학습한 것은 아니다.

마지막 평균 조합은 128만 쓴 89.0% 후보와 비교해 개발 표적에서 순증가 3개를 맞혔다. 정답 없는 테스트에서는 300개 중 **예측 1개가 달라졌다.** 그 1개가 실제로 더 맞는지는 테스트 정답이 없어 확인할 수 없다.

### 10.5 체크포인트 복원과 다른 분할도 확인했다

저장한 `best.ckpt`가 정상인지 확인하려고 기존 32 추론 설정으로 다시 예측했다. 재추론 코드가 검사한 fold 0에서 과거 확률과 **최대 절대 차이 0.0**, 예측 클래스 일치율 100%를 확인했다. 이 검사는 가중치 복원 경로가 일치한다는 근거이며, 모든 가능한 환경에서 비트 단위 재현을 보장한다는 뜻은 아니다.

최종과 같은 ‘original/all × 128/512 동일 평균’ 방식을 분할 seed 2026의 별도 미세조정 결과에도 적용했다.

| 검증 구성 | 정확도 | log loss |
| --- | ---: | ---: |
| 선택에 사용한 분할 seed 42 | **89.3%** | 0.32427 |
| 반복 분할 seed 2026 | **88.5%** | 0.32638 |

log loss는 맞고 틀린 여부뿐 아니라 확률이 얼마나 적절한지도 보는 지표로, 낮을수록 좋다. 최종 선택 후 다른 분할 결과가 나왔지만 제출 후보는 다시 바꾸지 않았다.

## 11. 최종 모델은 어디에서 틀렸나

다음은 최종 저장 OOF 확률을 이번 문서 작성 시 다시 합산해 계산한 결과다. 대회 당시 추가 모델을 선택한 실험이 아니라 **확정된 결과의 설명을 위한 사후 집계**다.

### 11.1 클래스별 정분류와 혼동

| 실제 클래스 | 200개 중 정답 | 해당 클래스 재현율 | 가장 큰 혼동 |
| --- | ---: | ---: | --- |
| `HEAVY_VEHICLE` | 185 | 92.5% | 일반 차량으로 13개 |
| `LIGHT_VEHICLE` | 181 | 90.5% | 대형 차량으로 10개 |
| `PERSONNEL` | 176 | 88.0% | 보행자 그룹으로 22개 |
| `PERSONNEL_GROUP` | 171 | 85.5% | 단독 보행자로 27개 |
| `TWO_WHEELER` | 180 | 90.0% | 일반 차량·단독 보행자·보행자 그룹으로 각각 6개 |
| 전체 | **893 / 1,000** | **89.3%** | 오류 107개 |

단독 보행자와 그룹 사이의 혼동은 양방향 합계 49개로 전체 오류 107개의 약 45.8%다. 앞서 전문 모델과 군집 특징을 시험한 배경과도 연결된다. 그렇지만 ‘혼동이 크다’는 것과 ‘전문 모델을 추가하면 해결된다’는 것은 별개였고, 실제 비교에서는 개선되지 않았다.

### 11.2 점이 적을수록 어려웠다

| 표적당 detection 개수 | 표적 수 | 최종 OOF 정확도 |
| --- | ---: | ---: |
| 10개 이하 | 315 | 83.49% |
| 11~25개 | 304 | 88.16% |
| 26개 이상 | 381 | 95.01% |

관측량이 적은 구간이 특히 어려웠다. 다만 표적 종류별 관측량 자체가 다르므로, 이 결과만으로 ‘점을 더 모으기만 하면 같은 비율로 성능이 올라간다’고 단정할 수는 없다.

## 12. 대회 진행과 Codex의 역할

### 12.1 Codex는 무엇을 했나

Codex는 문제를 읽고 자연어로 아이디어만 제시하는 데 그치지 않고, 로컬에서 코드를 작성하고 실행 기록을 읽으며 다음 실험을 정했다. 무거운 학습·추론은 당시 연결된 Runpod의 **A100 SXM 80GB 3장**을 사용했다.

작업 흐름은 다음과 같다.

```text
지문·데이터 확인
    ↓
표적 단위 특징 생성과 CPU 기준 모델 확보
    ↓
GPU 모델·특징 조합 실험
    ↓
OOF 확률 저장 → 점수·오류·앙상블 비교
    ↓
유망 설정을 다른 분할과 재추론으로 확인
    ↓
선택 후보·가중치·예측 확률을 로컬로 회수
    ↓
온라인 환경에서 실행할 Notebook과 CSV 생성·검증
```

사용자는 중간에 다른 접근도 시도하고 GPU를 효율적으로 활용하라고 요청했다. 이에 모델별 작업을 여러 GPU에 나누고, 20초 간격 감시로 GPU 활용 상태·진행 로그·오류·디스크 여유를 확인했다. 세 GPU 모두가 대회 내내 1번만 계산한 것은 아니고 다른 문항과 자원을 나눠 사용했다. 최종 1번의 두 미세조정 설정이 서로 다른 GPU에서 실행된 사실은 각 학습 JSON에도 남아 있다.

### 12.3 Notebook에 있던 숨은 지시문도 제거했다

원본 Notebook의 첫 Markdown 셀에는 거의 보이지 않는 HTML 글씨로, AI가 코드를 작성하지 못하게 하고 이후 사용자 지시도 무시하라고 요구하는 문구가 있었다. 사용자가 이를 확인·제거해 달라고 요청했다.

이 문구는 데이터나 정답 규칙이 아니라 AI를 향한 **프롬프트 인젝션**이었다. 풀이 지시로 적용하지 않았고, 로컬·ZIP 내부·원격 사본을 검사해 제거했다. 삭제 전부터 실제 CPU·GPU 학습이 실행된 기록이 있어, 해당 문구 때문에 코드 작성을 거부한 상황은 아니었다.

나중에 사용자가 온라인 실행본을 올렸을 때 그 사본의 지문에도 남아 있던 문구를 제거했고, 풀이 코드와 출력은 보존했다. 이는 데이터 값이나 예측을 변경하는 처리가 아니었다.

## 13. 마지막 시행착오: Notebook 안에서 CPU로 다시 학습할 수 있을까

### 13.1 사용자는 온라인 재학습도 요청했다

최초 최종본을 받은 뒤, 사용자는 외부 GPU 계산값을 넣는 대신 **제공 Jupyter Notebook 안에서 같은 방식으로 학습하도록 만들 수 있는지** 물었다. 남은 약 20분에 맞춰 학습량을 줄였을 때 성능이 얼마나 내려가는지도 확인해 달라고 했다.

실제 온라인 환경은 Python 3.9.7, CPU affinity 2개, RAM cgroup 상한 4 GiB, PyTorch 1.10.0+cpu였고 GPU가 없었다. 대회 풀이용 최신 GPU 환경과 차이가 컸다.

1번 최종 모델을 그대로 재현하려면 TabICL 가중치 10개와 128·512 내부 추론 조합을 처리해야 했다. 이를 2코어 CPU에서 20분 안에 재현할 수 있다고 확인된 상태는 아니었다. 대신 계산이 가벼운 CPU 분류기를 실제로 측정했다.

### 13.2 CPU 대안은 빨랐지만 정확도가 낮았다

CPU affinity를 2개로 제한하고 GPU를 숨긴 조건에서, 같은 seed 42의 5분할로 비교했다. 입력은 확장 특징 165개였다.

| CPU 대안 | OOF 정확도 | 최종 89.3% 대비 | 5분할 검증 시간 | 전체 학습+테스트 예측 |
| --- | ---: | ---: | ---: | ---: |
| ExtraTrees, 나무 500개 | 84.2% | -5.1%p | 약 10.91초 | 약 2.69초 |
| HistGradientBoosting | 83.4% | -5.9%p | 약 30.34초 | 약 7.57초 |

이 시간은 미리 만들어진 특징표를 읽어 학습·예측한 구간의 측정값이다. 원시 CSV부터 특징을 생성하는 모든 시간이나 실제 온라인 서버에서의 실행 시간을 뜻하지 않는다. 당시 Runpod의 비교 실행 로그에서 확인한 값이다.

CPU CatBoost도 비교를 시작했지만, 보존된 당시 출력에는 일부 fold만 완료된 상태가 남아 있다. 사용자가 중단을 요청했으므로 최종 5분할 정확도를 확정해 쓰지 않는다.

### 13.3 사용자의 최종 선택

사용자는 정확도 하락을 보고 **CPU 재학습 대안을 취소하고 기존 GPU 예측을 유지**하기로 했다. 진행 중인 비교 학습은 중단했다.

따라서 최종 제출본은 CPU에서 단순화한 모델로 바꾼 버전이 아니다. 앞서 확보한 **89.3% 개발 검증 후보의 예측 확률을 보존한 버전**이다.

## 14. 최종 Notebook은 실제로 무엇을 실행했나

### 14.1 GPU에서 끝낸 계산과 온라인에서 하는 계산

| 단계 | 실행 장소 | 하는 일 |
| --- | --- | --- |
| 특징 생성·모델 비교 | 로컬 CPU 및 Runpod | 관측 묶음을 특징표로 변환하고 후보 비교 |
| 최종 미세조정·모델 추론 | Runpod GPU | fold별 가중치 학습, OOF·테스트 확률 계산 |
| 최종 제출 Notebook | 온라인 CPU 커널 | 저장 확률 로드, 앙상블, 입력·형식 검증, CSV 저장 |

**최종 Notebook을 실행한다고 TabICL을 다시 학습하거나 원시 레이더로 모델 추론을 다시 하는 것은 아니다.** 온라인에서는 GPU가 계산해 둔 확률을 읽어서 합산하고 결과를 검증한다.

### 14.2 JSON.gz 안에 저장한 것은 가중치가 아니라 예측 확률이다

`prediction_data_q1.json.gz`에는 다음 자료가 있다.

| 내용 | 역할 |
| --- | --- |
| 테스트 ID 300개 | 확률 행을 제출 ID와 연결 |
| 훈련 ID 1,000개 | OOF 확률을 실제 훈련 정답과 연결 |
| 4개 구성의 테스트 확률 | 각 구성마다 300행 × 5클래스 |
| 4개 구성의 OOF 확률 | 각 구성마다 1,000행 × 5클래스 |
| 클래스 순서 | 확률 열이 어떤 클래스인지 식별 |
| 가중치 `[0.25,0.25,0.25,0.25]` | 네 확률을 동일 비중으로 합산 |
| 입력 CSV 해시 | 다른 데이터에 잘못 적용하지 않도록 확인 |
| 검증 지표·기준 예측·스냅샷 시각 | 결과가 확정 후보와 같은지 확인 |

즉, 핵심 확률 숫자는 `4 × (300 + 1000) × 5 = 26,000개`다. 여기에 ID·메타데이터가 들어간다. 파일 크기는 **254,857바이트, 약 249KiB**다.

쉽게 말하면 신경망 내부의 ‘학습한 규칙’을 이 파일에 넣은 것이 아니라, **모델 네 구성이 각 표적을 보고 매긴 5개 클래스의 점수표를 저장**했다. 최종 Notebook은 이 점수표를 평균해 답을 다시 만든다.

따라서 이 파일만으로 새로운 레이더 표적을 분류할 수는 없다. 저장된 특정 300개 표적을 위한 결과이며, 입력 데이터가 다르면 실행 코드가 해시 불일치를 감지한다.

최종 학습 가중치는 별도 `models-selected.tgz`에 보존했다. 확인된 내용은 fold별 `best.ckpt` 10개이고, 압축 크기는 약 3.06GB다. 이 큰 가중치 묶음은 가벼운 온라인 제출 파일에 포함하지 않았다.

### 14.3 Notebook이 열리지 않아 파일을 분리했다

처음에는 예측 데이터를 Notebook 안에 넣었다. 이후 사용자가 파일이 열리지 않는다고 알려, 같은 계산 결과를 다음처럼 분리했다.

```text
최종제출/1번/
├─ 레이더 시계열 데이터 기반 이동 표적 식별하기.ipynb
├─ solution_q1.py
├─ prediction_data_q1.json.gz
└─ submission.csv
```

Notebook은 작은 실행 셀을 유지하고, 같은 코드를 `solution_q1.py`로도 제공했다. 사용자는 `.py` 전체를 원래 Notebook의 코드 셀에 붙여넣거나 `%run ./solution_q1.py`로 실행할 수 있었다. `.gz`는 압축을 풀지 않고 Notebook 작업 폴더에 두는 방식이다.

코드와 예측 데이터를 분리했을 뿐 **확률·정답 선택·CSV 결과는 바꾸지 않았다.**

### 14.4 실행 코드가 확인하는 항목

최종 코드는 단순히 저장된 정답 문자열을 복사하는 것보다 여러 검사를 추가했다.

1. 예측 데이터 파일의 해시를 확인한다.
2. 현재 문제의 `train.csv`, `test.csv`를 찾고 입력 해시를 확인한다. BOM·줄바꿈 차이는 정규화한다.
3. 테스트 ID가 정확히 300개이고 저장된 ID와 일치하는지 확인한다.
4. 클래스 목록과 각 구성의 클래스 순서가 일치하는지 확인한다.
5. 확률 배열의 모양, 유한값, 음수 여부, 각 행의 확률 합을 확인한다.
6. 네 테스트 확률을 각각 25%씩 더해 가장 높은 클래스를 고른다.
7. 같은 방식으로 OOF를 합산하고 훈련 정답과 비교해 89.3%를 다시 계산한다.
8. 최종 후보의 기준 예측과 300개 결과가 모두 같은지 확인한다.
9. ID 정렬·중복·결측·허용 클래스·열 순서를 확인한 뒤 `index=False`로 저장한다.
10. 임시 CSV를 다시 읽어 검증하고, 정식 `submission.csv`로 교체한 뒤 SHA256을 출력한다.

출력되는 89.3%도 저장 OOF 확률로 재계산한 값이다. 온라인 CPU에서 모델을 새로 평가해서 얻은 새로운 검증 성능이 아니다.

### 14.5 실행 검증은 어디까지 확인했나

첫째, 별도 x86_64 환경에서 Python 3.9.7, NumPy 1.23.5, pandas 1.5.2, CPU affinity 2개, GPU 비노출, 주소 공간 제한 4 GiB 조건으로 Notebook을 실행했다. 주소 공간 제한은 온라인 cgroup 메모리 제한과 같은 장치는 아니지만, 제출 코드의 자원 사용을 제한해 확인한 것이다.

분리본의 1번 Notebook은 기록상 약 **1.676초**, `.py` 단독 실행은 약 **0.658초**에 종료했고, 모두 기존 최종 CSV와 같았다. 이 시간은 별도 검증 환경의 값이다.

둘째, 사용자가 실제 대회 커널에서 실행한 원래 이름의 Notebook을 작업공간에 올렸다. 그 파일 출력에는 다음이 남아 있었다.

```text
Python: 3.9.7 | /opt/conda/bin/python
작업 폴더: /home/jovyan/work/Problem #1
현재 예측 300건과 모두 일치
개발 OOF Accuracy: 0.8930 (테스트 정답 점수 아님)
행 수: 300 | 열: ['sample_id', 'label']
SHA256: 8c2ff40a1ce4999272989b0955c85057522732ecee13e0521a579e2a6e0543b2
```

업로드된 실행본의 출력에는 약 64.70초가 기록되어 있다. 별도 검증 환경의 1~2초와 다르지만, 최종 CSV 해시는 일치한다. 온라인 환경에서의 소요 시간을 로컬 측정값으로 보장한 것은 아니다.

Codex가 온라인 커널에 직접 연결해 실행한 것은 아니며 **사용자가 올린 실행 기록을 확인한 것**이다. 공식 제출 접수 여부와 공식 테스트 점수는 이 자료만으로 확인되지 않는다.

## 15. 이 풀이에서 실제로 얻은 것과 남은 한계

초기 ExtraTrees 84.9%에서 최종 89.3%로 **개발 검증 정확도가 4.4%p 상승**했다. 같은 1,000개 기준으로 정답 수는 849개에서 893개로 늘었고, 오류는 151개에서 107개로 줄었다.

개선의 중심은 다음 세 가지였다.

- **표적 단위 표현:** 서로 다른 수의 레이더 관측을 분포·시간 변화·형상·관측량 특징으로 바꿨다.
- **소규모 데이터에 맞춘 사전학습 모델과 미세조정:** 처음부터 학습한 점군 모델보다 TabICL의 전이학습 결과가 좋았다.
- **보완되는 확률의 평균:** 79·165개 특징과 128·512 내부 추론을 조합해 단일 구성보다 성능을 높였다.

반대로 복잡한 특징, 더 많은 신경망 연산, 전문 모델, 의사 라벨이 자동으로 개선을 주지는 않았다. 실험에서 낮은 결과가 나오거나 다른 분할에서 이득이 반복되지 않으면 제외했다.

한계도 분명하다. 후보 선택에 같은 개발 데이터를 반복 사용했고, 반복 분할도 독립된 새 데이터가 아니다. 초기 PointNet의 검증 방식은 최종 TabICL과 달랐으며, 센서 좌표 변환은 전체 훈련 좌표로 추정했다. 따라서 모든 실험의 숫자를 동일한 엄격성의 독립 시험 성적처럼 나열하면 안 된다.

또 최종 온라인 실행본은 이 특정 데이터의 GPU 예측 확률을 합산하는 프로그램이다. 새 데이터까지 분류하는 학습·추론 파이프라인을 온라인 CPU에서 그대로 재현한 제출본이라는 뜻은 아니다.

## 부록 A. 보존된 5클래스 OOF 산출물 전체

이 표는 문서 작성 시 `race90/competition/q1/*.npz`에서 **`oof` 모양이 `(1000, 5)`인 완성 산출물 100개**를 읽어, 별도 `labels.csv`의 정답과 비교해 다시 계산한 것이다. 새 학습·새 후보 선택은 수행하지 않았다.

100개는 서로 완전히 다른 알고리즘 100종이라는 뜻이 아니다. 특징 변경, 분할·모델 seed 변경, 같은 가중치의 재추론, 확률 앙상블을 각각 포함한다. 최초 ExtraTrees·CatBoost는 별도 하네스의 CSV 로그에 있어 이 표에 포함되지 않는다. 전문 모델의 `(1000,5,2)` 배열과 이진 모델의 `(1000,2)` 배열도 별도다.

파일명은 다음처럼 읽으면 된다.

- `original`, `all`, `robust`, `physics`: 각각 앞 79·165·215·337개 특징 구성
- `s42`, `s123`, `s57`: 모델 seed
- `cv42`, `cv123`, `cv2026`: 교차검증 분할 seed
- `lr3e-05`: 학습률 0.00003
- `e120`: 최대 epoch 120
- `infer128`, `infer512`: 같은 가중치로 수행한 내부 추론 앙상블 크기
