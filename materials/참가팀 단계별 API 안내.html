공통 규칙

  • 서버 주소는 http://<서버IP>:8000, 모든 창구는 /api/report/ 아래에 있습니다(리허설 경기는 /api/rehearsal/ — 부록)
  • 임무코드로 팀을 확인합니다 — GET은 ?mission_code=, POST는 본문의 "mission_code". 영문+숫자 8자리, 대소문자 무관

  • 미결·잠정 항목을 확정처럼 코드에 박지 마세요

시간 — 미리 알려 드립니다

시작 신호부터일
0:00경기 시작 · 1차 임무(전술명령) 게시 · UGV 출발(잠금 해제) — 2·3단계

시간은 팀이 잽니다

  • 서버는 남은 시간을 주지 않습니다 — 로봇이 시작 신호를 받은 순간부터 팀 프로그램이 자기 시계로 잽니다
  • 경기는 시작 후 5분 진행, 4:00에 2차 임무, 끝나면 보고 30초입니다
  • M5 점령이 나오면 5:00 전에 끝날 수 있습니다 — 끝은 팀 시계가 아니라 보고(report) 신호로 압니다(10단계)
  • 1·2차 임무는 wait를 붙여 물어 두면 게시되는 순간 받습니다(2·9단계)
이 파일에는 접속 정보를 넣지 않았습니다 — 서버 주소·임무코드는 현장에서 따로 안내합니다. 예시의 팀 이름·토큰·시각은 꾸민 값입니다. 경기 규칙의 원본은 경기 룰북, 참가팀 규약의 원본은 SERVER ↔ UGV 통신 규약(배포본)입니다.
1

준비완료

준비 단계 참가팀 구현 · 필수확정

준비 단계가 되면 주최측 경기 노드가 팀 프로그램(team_node.py)을 실행합니다. 프로그램은 모델·필수 센서 초기화가 성공한 뒤 /me로 지금 단계를 보고, 임무코드만 실어 준비완료를 보냅니다. 사람이 누르는 단추가 아닙니다. 안 보내면 그 팀을 빼고 시작할 수 있고, 빠진 경기는 0점입니다.

순서

  1. GET /api/report/me로 우리 팀 상태를 봅니다
  2. phase가 "ready"이고 ready가 false면 →
  3. POST /api/report/ready에 {"mission_code": …}만 보냅니다
  4. 200 · {"accepted": true}면 끝. 409이거나 통신이 실패하면 2초 뒤 1번부터 다시

/me 응답 필드

필드뜻
slot이번 경기의 우리 자리 = 호출부호 — B-1~B-3 · R-1~R-3. 앞 글자가 진영(B = BLUE, R = RED)이다. 이번 경기에 편성되지 않았으면 null
camp우리 진영 — BLUE · RED. 편성되지 않았으면 null
phase지금 경기 단계 — 아래 표
ready이번 경기에서 서버가 우리 준비완료를 받아 둔 상태인가 (true/false)

phase 값

값단계뜻
idle대기 전경기가 열리지 않음. 팀 프로그램은 아직 실행되지 않습니다
waiting대기운영진이 UGV를 점검하고 자리에 놓는 시간. 준비완료는 아직 받지 않습니다(409)
ready준비UGV에 경기 설정이 들어가 잠기고 팀 프로그램이 실행됩니다. 준비완료를 보내는 단계
running진행경기 중(0:00~5:00). 임무 받기·M1·M3 보고
reporting보고경기가 끝나 UGV는 잠기고, M6를 받는 30초. 팀 프로그램은 아직 실행 중입니다
finished종료보고 시간이 끝남. 팀 프로그램이 종료됩니다

오류

401임무코드가 틀렸습니다 — 「임무코드가 올바르지 않습니다」
409지금 받을 수 없습니다 — 준비 단계가 아님 · 경기 시작 직전 · 이번 경기에 편성되지 않음 · 「UGV 경기 설정이 아직 확인되지 않았습니다 — 잠시 뒤 다시 보내세요」. 2초 뒤 다시 시도하면 됩니다

알아 둘 것

  • 프로그램이 도중에 다시 실행돼도 위 순서대로 /me부터 보면 됩니다 — 이미 받아 둔 준비완료는 ready: true로 보입니다
  • 서버는 「모델이 정말 다 불러졌는지」 알 수 없습니다 — 초기화가 끝난 뒤 보내는 것은 팀이 지킵니다
2

임무(전술명령) 받기

0:00 참가팀 구현 · 필수확정

경기 시계가 흐르는 0:00에 임무(전술명령 문장)가 서버에 게시됩니다. 서버가 먼저 보내 주지 않습니다 — 팀이 요청해서 받습니다. 이 명령문을 해석한 결과가 5단계 M1 보고입니다.

순서

  1. GET /api/report/order에 임무코드와 wait=120을 실어 묻습니다 — 준비완료를 보낸 뒤 바로 걸어 두면 됩니다
  2. 서버가 게시될 때까지 응답을 붙잡고 있다가 게시되는 즉시 돌려줍니다
  3. accepted가 false면 아직 게시 전입니다(120초 동안 게시가 없었음) — reason에 이유. 오류가 아닙니다(200). 다시 요청합니다
  4. accepted가 true면 order.tactical_command가 임무 명령문입니다

기다리는 요청 — wait

값뜻
wait 생략 · 0바로 답합니다 — 게시 전이면 accepted: false
wait=1~120게시될 때까지 최대 그 초만큼 기다렸다가, 게시되는 즉시 기다리던 모든 팀에 같은 순간 돌려줍니다. 이미 게시됐거나 편성 밖이면 바로 답합니다
  • 최대 120초입니다 — 그 안에 게시가 없으면 accepted: false가 오니 다시 요청합니다(같은 요청에는 늘 같은 답)
  • HTTP 클라이언트 타임아웃은 wait보다 길게 잡습니다 — 짧으면 서버가 답하기 전에 클라이언트가 먼저 끊습니다
  • 기다리는 동안 응답이 오지 않으므로 주행·인식 같은 메인 루프를 막지 않게 따로(배경에서) 기다립니다
  • 프로그램이 다시 실행돼 시작 시각을 잃어도, 시작부터 wait를 걸어 두면 게시되는 순간에 받습니다

응답 필드

필드뜻
accepted임무를 받았는가 — true면 order가 함께 오고, false면 reason만 옵니다
reasonaccepted가 false일 때만 — 받지 못한 이유(아래 표)
orderaccepted가 true일 때만 — 우리 팀에 게시된 임무
order.tactical_command전술명령 문장 — 5단계에서 해석해 M1으로 보고할 원문. 팀마다 다를 수 있습니다
order.issued_at서버가 게시한 시각 — 한국 시간 YYYY-MM-DD HH:MM:SS

이 경기에 편성되지 않은 팀입니다이번 경기에 우리 팀이 없습니다 — 기다려도 오지 않습니다
게시된 임무가 없습니다0:00이 지났는데 게시가 없습니다 — 주최측에 알리세요

오류

게시 전·편성 밖은 오류가 아니라 200 · accepted: false입니다(위 reason 표).

알아 둘 것

  • 게시된 뒤에는 몇 번을 물어도 같은 내용이 돌아옵니다 — 경기가 끝난 뒤에도, 팀 프로그램이 다시 실행된 뒤에도
  • 목표거점은 여기 없습니다 — 9단계 /api/report/target
  • 남의 팀 임무는 받을 수 없습니다 — 임무코드의 팀 것만 옵니다

출발 · 주행

0:00 → 경기 끝 주최측 처리주행 · 젯슨 API 규격서

출발·주행에는 서버 API가 없습니다 — 출발 신호는 주최측이 UGV로 보내고, 로봇 쪽은 젯슨 API 규격서를 따릅니다. 이 장은 서버 창구와 맞물리는 시각만 정리합니다.

서버와 맞물리는 시각

시작 신호부터서버 쪽
0:00경기 시작 — 1차 임무가 서버에 게시되고(2단계 /api/report/order) UGV가 출발합니다. 이때 잠금이 풀립니다
4:002차 임무(M5 목표거점) 게시 — 9단계
5:00진행 끝 → 보고 단계 — 10단계 (M5 점령이 나오면 더 일찍)
  • 시작 신호를 받은 순간부터 팀이 자기 시계로 시간을 잽니다 — 서버는 남은 시간을 주지 않습니다(표지 「시간」)
  • 시작 신호를 받은 때가 곧 경기의 0:00입니다
  • 서버 쪽에서는 /api/report/me의 phase가 "running"이면 경기 중입니다(1단계)
4

드론 화면 받기

진행 중 · 연습 기간 참가팀 구현 · 선택서버 창구 확정

상공 카메라 화면을 서버가 1초마다 캡처해 두고, 팀은 가장 최신 정상 한 장을 JPEG로 받습니다. 요청은 두 가지입니다 — 경기 때는 camera 없이, 연습 기간 테스트는 camera를 반드시 붙여서.

요청 두 가지

쓰임요청받는 것
경기camera 없음 지금 경기에 편성된 팀이 진행 중일 때만(그 밖에는 409). 본선 카메라. 우리 진영 시설물(상대 팀의 지정표적)이 1개 파괴되면 2초 · 2개면 5초 간격으로만 새 장, 3개면 받을 수 없습니다(403)
연습camera 붙임 주최측이 테스트 모드를 켠 연습 기간에만. 편성·경기와 상관없이 1초마다 최신 장, 저하 없음

camera 값

값카메라

  • 연습 기간 테스트는 camera를 반드시 붙입니다. 안 붙이면 테스트 모드여도 경기 요청으로 보고 편성·진행을 확인합니다 — 경기 밖이면 409
  • 경기 때는 camera를 빼고 부르세요. 테스트 모드가 꺼져 있으면 camera는 무시되고 경기 규칙이 적용됩니다

알아 둘 것

  • 깨진 화면은 주지 않습니다 — 영상이 깨지면 다음 정상 화면까지(몇 초) 마지막 정상 화면이 옵니다. X-Captured-At으로 찍힌 시각을 확인하세요
  • 1초보다 자주 불러도 새 장이 더 빨리 나오지는 않습니다
  • 점수와 직접 관계는 없고, 판단(M6 등)에 쓰고 싶은 팀이 씁니다

M2 지정표적 타격

진행 중 사격 · 젯슨 API 규격서판정 · 주최측 장치

서버가 팀마다 지정한 상대 진영 표적 1개를 레이저로 맞힙니다. 참가팀이 API로 보고하는 것은 없습니다 — 표적 장치가 판정해 서버로 보냅니다. 배점 15 — 지정표적 유효타격 10 + 연합 세 팀의 지정표적이 모두 성공하면 각 5.

판정 순서

  1. 표적의 수광부에 2초 연속 비추면 표적 장치가 피격으로 판정합니다
  2. 판정 결과는 표적 장치가 서버로 보냅니다
  3. 누가 쏘든(상대 팀·아군 오사 포함) 지정표적이 부서지면 그 표적을 지정받은 팀의 점수입니다 — 연합 보너스도 같은 방식으로 셉니다
  4. 표적은 경기마다 처음 부서질 때 한 번만 인정됩니다 — 부서진 표적을 다시 맞혀도 점수가 더 오르지 않습니다

알아 둘 것

  • 어느 표적이 우리 지정표적인지는 따로 알려 주지 않습니다 — 2단계 임무 명령문에 들어 있습니다
  • 지정표적은 진영마다 셋 — 통신시설 · 감시초소 · 레이더시설. 놓일 수 있는 자리는 공개되고, 어느 자리에 어느 종류가 놓이는지는 경기마다 다릅니다
  • 우리 진영 표적이 파괴되면 우리 드론 화면이 느려집니다(4단계)
  • 표적이 부서졌는지는 서버가 참가팀 API로 알려 주지 않습니다

M5 목표거점 받기

4:00 (종료 60초 전) 참가팀 구현 · 필수확정

종료 60초 전에 진영별 목표거점 한 곳이 게시됩니다. 2단계와 같은 방식으로 팀이 요청해서 받습니다. 그 거점에 가장 먼저 들어간 연합이 M5 점수를 받고, 점령하는 순간 진행이 끝납니다(10단계). 배점 10 — 점령한 연합의 세 팀이 각 10(점령한 팀 몫이 따로 있지 않습니다). 경기가 끝나면 두 연합의 합계를 비교해 이긴 연합 세 팀이 각 5(연합 승리 — 무승부면 양쪽 모두 5)를 더 받습니다.

순서

  1. GET /api/report/target에 임무코드와 wait=120을 실어 묻습니다 — 경기 시작부터 걸어 두면 됩니다
  2. 서버가 게시될 때까지 응답을 붙잡고 있다가 게시되는 즉시(4:00) 돌려줍니다 — 모든 팀이 같은 순간에 받습니다
  3. accepted가 false면 아직 게시 전입니다(120초 동안 게시가 없었음) — reason에 이유. 오류가 아닙니다(200). 다시 요청합니다
  4. accepted가 true면 order.objective_label이 가야 할 거점입니다
  • wait는 2단계와 같습니다 — 최대 120초 · HTTP 클라이언트 타임아웃은 wait보다 길게 · 메인 루프를 막지 않게 따로(배경에서) 기다립니다
  • 4:00은 시작 신호부터 팀이 잰 시각입니다 — 서버는 남은 시간을 주지 않으니, 시각을 맞춰 묻기보다 wait로 걸어 두는 편이 정확합니다. 프로그램이 다시 실행돼 시작 시각을 잃어도 wait를 걸어 두면 게시 순간에 받습니다

경기 종료

5:00 · 또는 M5 점령 순간 주최측 처리실기 확인 예정

경기 시간 5분이 끝나거나, 어느 연합이든 목표거점을 점령하면 그 순간(9단계) 진행이 끝납니다. 주최측이 UGV를 멈추고 잠급니다(로봇에는 보고 report 신호가 갑니다 — 젯슨 API 규격서). 팀 노드는 꺼지지 않습니다 — M6 보고 시간이 끝나면 그때 팀 노드가 종료됩니다.

순서

  1. 진행이 끝나면 서버가 먼저 /api/report/me의 phase를 "reporting"(보고)으로 바꾸고, 그다음 로봇에 보고(report) 신호를 보냅니다
  2. 로봇이 /mil/match로 report(경기 끝)를 알리면 11단계 M6를 보냅니다 — 로봇 쪽 처리는 젯슨 API 규격서를 따릅니다
  3. 보고 시간이 끝나면 phase가 "finished"(종료)가 되고 주최측이 팀 프로그램을 종료합니다

보고 단계 확인

  • report = 경기 끝입니다. 일시정지 pause는 경기 중 잠깐 멈춤(주최측과의 통신이 끊겼을 때 등 — 이어서 재개나 report가 옵니다)이라 M6를 보내지 않습니다 2026-10-27
  • 서버 GET /api/report/me의 phase가 "reporting"인지로도 알 수 있습니다 — 보고 단계가 아니면 서버가 M6를 409로 받지 않습니다
  • M5 점령이 나오면 5:00 전에 끝날 수 있습니다 — 팀 시계로 5:00을 기다리지 말고 report 신호로 압니다

지킬 것

  • 경기 종료는 /me의 phase로 압니다 — "running"에서 "reporting"으로 바뀐 때
  • 이때부터 M1·M3는 받지 않습니다(409). 받는 것은 11단계 M6뿐입니다
  • M6 보고 시간은 30초입니다. 남은 시간은 따로 알려 주지 않습니다 — 서버가 보고 단계로 바꾼 순간부터 셉니다. 여섯 팀이 다 내면 바로 끝납니다
  • 보고 시간이 끝나면 팀 프로그램이 끝나므로 그 뒤에는 보고가 나가지 않습니다

M6 위험도 보고

종료 후 30초 참가팀 구현 · 보고JSON 형식 임시

경기가 끝난 뒤 상대 세 팀의 위협도 1·2·3순위를 보고합니다. 배점 15 — 셋 다 일치 15 · 1순위만 10 · 2·3순위 중 하나 5. 서버 정답은 상대 세 팀의 위험도가 높은 순입니다 — 위험도 = 남은 목숨/4 + 남은 탄/8 + M3 점수/30(셋이 같은 무게, 0 밑으로 내려가지 않음). 여섯 팀이 다 내면 보고 시간이 바로 끝납니다.

순서

  1. 순위는 경기 중에 미리 만들어 둡니다
  2. /me의 phase가 "reporting"이 되면(10단계 「보고 단계 확인」) →
  3. 바로 상대 세 팀을 위험한 순서로 POST /api/report/situation에 보냅니다 — 409면 잠시 뒤 다시
  4. 고쳐 보내면 마지막 것이 남습니다 — 30초 안에

30초는 서버가 보고 단계로 바꾼 순간부터라 팀 시계보다 먼저 시작합니다 — 마감도 서버가 받은 시각 기준이니, 보고 단계가 되면 지체 없이 보냅니다.
