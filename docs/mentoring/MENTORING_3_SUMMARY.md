# 국방 AI 경진대회 3차 멘토링 요약

- 영상 날짜: **2026년 11월 6일(금)**
- 길이: **1시간 1분 9초**
- 주제: 본선 참가·일정 안내, UGV 개발 환경, ROS 2 제어 API, 경기 서버 API 구현 방법
- 확인 범위: **전체 음성의 자동 전사와 주요 화면 표기 대조**. API·점수 자료는 영상 당시 안내이며, 멘토는 **본선 오리엔테이션에서 최종 API 문서를 다시 제공**한다고 명시했다.

## 핵심 7가지

1. **본선은 11월 18~20일, 경기 화성시 YBM연수원에서 열린다.** 첫날 오전10시 입소가 원칙이며, 운영진은 늦더라도 정오까지 도착해야 한다고 설명했다. 마지막 날 발표자료는 오전8시까지 제출한다. 발표평가20%와 임무평가80%를 합산한다.
2. **참가팀 프로그램 `team_node.py`가 두 통신 체계를 연결한다.** 로봇의 센서·주행·조준·발사는 ROS 2 Topic/Service로 처리하고, 임무 수신·준비완료·결과 보고는 HTTP GET/POST와 JSON으로 경기 서버에 통신한다. 두 API를 묶어 자율임무를 구현해야 한다.
3. **경기 상태에 따라 로봇 제어와 보고 가능 여부가 달라진다.** ROS 2 `/mil/match`의 경기 명령과 HTTP `GET /api/report/me` 응답의 `phase`를 확인한다. `pause`는 일시중단이고 `report`는 진행 종료 후 보고 단계이므로 구별해야 한다.
4. **서버는 전술명령과 M5 목표거점을 먼저 보내주지 않는다.** 참가팀이 GET 요청으로 받아야 한다. `wait`를 사용해 최대120초 대기할 수 있으나, 주행·인식 루프를 막지 않도록 별도로 처리한다. `accepted:false`가 정상200 응답인 경우도 있다.
5. **M1·M3는 경기 진행 중 제출하고, 수정 시 전체 결과를 다시 보낸다.** M1은 지정표적·탐색 섹터·목표거점의 해석 결과, M3는 섹터별 객체 종류·개수다. 서버가 받은 마지막 제출을 채점하므로 마감 직전에 몰아서 보내지 말아야 한다.
6. **M5는 경기4분에 게시되고 점령 즉시 경기가 끝날 수 있다.** 5분을 기다리는 구현은 늦을 수 있다. 종료 후에는 서버가 `reporting` 단계로 바뀐 순간부터30초 안에 M6 상대 UGV 위험도 순위를 제출한다.
7. **배터리 관리와 통신 예외처리가 실제 임무의 기본 조건이다.** 충전식 배터리는 교체가 불가하며 잔량이 구동부·센서·Jetson 동작에 영향을 줄 수 있다. API 지연·응답 누락·통신 실패를 처리하고, 채점은 전송 시각보다 **서버가 수신·저장한 데이터**를 기준으로 이해해야 한다.

## 개발 환경과 ROS 2 API

**WINGBOT-UGV**는 Jetson Orin Nano 기반이며 카메라·LiDAR·레이저·수광부 센서 등을 갖춘다. 멘토는 로봇에 접속한 JupyterLab에서 기본 안내를 포함한8개 예제를 소개한다. 노트북 실행 커널은 **`Python 3 (ROS 2)`**다. (17:58~21:51)

| 기능 | ROS 2 경로 | 핵심 사항 |
| --- | --- | --- |
| 로봇 상태 | Topic `/mil/state` | HP·최대HP·배터리, 상태 갱신2Hz |
| 경기 상태 | Topic `/mil/match` | `practice`/`mission` 모드와 경기 명령 확인. 경기 모드의 제어 허용은 `start`/`resume` |
| OLED | Topic `/mil/oled` | `line`, `text`. 4줄(0~3), 한 줄 최대21자, 전송 간격0.5초 이상, 마지막 출력10초 후 기본 화면 복귀 |
| 팬틸트 | Service `/mil/gimbal` | `pan`, `tilt`는 -100~100의 **위치값**. pan1단위0.5°, tilt1단위0.15°. `speed`, `acc`도 설정 |
| 주행 | Topic `/cmd_vel` | `Twist` 발행. `linear.x` 전후 속도(-0.6~0.6m/s), `angular.z` 회전 속도(-3~3rad/s) |
| 위치 | Topic `/odom` | `Odometry` 구독, 위치·방향 확인,20Hz |
| 레이저 | Service `/mil/fire` | 발광5초, 발사 시작 후10초 지나면 재발사 가능. `fired`/`empty`/`locked`/`reloading` 응답 |
| 카메라 | Topic `/image_raw` | 640×480, 최대30FPS. CPU 사용량 때문에10FPS 이하 권장. 예제는 한 장만 표시 |
| IMU | Topic `/imu/data` | Roll·Pitch·Yaw·가속도 확인. `/odom`과 함께 자세·위치 파악 |

Topic은 지속적인 데이터 발행·구독에, Service는 특정 동작 요청과 결과 확인에 사용한다. 연습 모드는 HP·탄약이 자동 회복되지만, 경기 모드는 그렇지 않다. 연습 중에도 피격 잠금·레이저 재발사 대기 같은 개별 제한은 적용된다.

멘토는 **Depth 카메라에 별도 API를 제공하지 않는다**고 설명했다. 전류 소비가 크므로 임무에 꼭 필요한 경우 사용하고 배터리를 관리해야 한다. 일반 카메라도 모든 프레임을 처리하기보다 팀의 모델 처리 속도에 맞춰 필요한 프레임만 사용해 실시간 성능을 유지하라고 권했다. (27:16~28:10)

ROS 2에서도 연결·수신이 항상 정상이라고 가정하면 안 된다. 서비스 요청에는 타임아웃·예외처리를 넣고, 카메라·IMU 데이터가 일정 시간 들어오지 않는 상황을 감지할 유효성 검사를 구현하라는 조언이 있다. (28:50~29:53)

하드웨어의 부품 추가·교체·변형과 기본 펌웨어 임의 변경은 금지된다. 개발은 제공 ROS 2 API와 허용된 환경 범위 안에서 진행한다. 화면에는 소프트웨어·코드 수정 및 다양한 라벨링 방식 활용이 가능하다고 안내되어 있다.

배터리는 전용 **12.6V/2A 충전기**를 사용하며, 충전 케이블이 연결된 상태에서는 모터를 구동하지 않는다. 화면 사양상 최대 소비전력 기준 사용시간은 약40분, 완충은 약3시간 내외다. Jetson 보드 어댑터와 배터리 충전기는 구별해야 한다.

## 경기 서버 API와 보고 흐름

아래는 **HTTP 경로**다. 자료에서 `/me`라고 줄여 쓴 것은 `/api/report/me`이며, `phase`는 그 **응답 JSON의 필드**다. ROS Topic인 `/mil/match`와 다른 체계다.

| 단계 | HTTP 요청 | 구현할 일 |
| --- | --- | --- |
| 상태 조회 | `GET /api/report/me` | `mission_code`를 보내고 `slot`, `camp`, `phase`, `ready` 확인 |
| 준비완료 | `POST /api/report/ready` | 모델·필수 센서 초기화 후, `phase:ready`·`ready:false`인 상태에서 임무코드 제출 |
| 전술명령 수신 | `GET /api/report/order` | `mission_code`, 선택적으로 `wait`. 응답의 `order.tactical_command` 해석 |
| 드론 화면 수신(선택) | `GET /api/report/drone` | 최신 정상 JPEG 한 장. 연습 테스트는 `camera=main/test1/test2`, 실제 경기는 `camera` 생략 |
| M1 보고 | `POST /api/report/interpretation` | `target`, `search_sectors`, `base`를 임무코드와 함께 제출 |
| M3 보고 | `POST /api/report/detection` | 섹터별 `objects`의 `type`, `count` 제출 |
| M5 수신 | `GET /api/report/target` | 목표거점이 게시되면 `order.objective`·`order.objective_label` 확인 |
| M6 보고 | `POST /api/report/situation` | 상대 호출부호를 위험한 순서대로 `ranking`에 제출 |

구현 시 특히 주의할 점:

- **준비완료는 프로그램이 보낸다.** 보내지 않으면 해당 팀을 제외하고 시작할 수 있고 그 경기는0점 처리될 수 있다.
- `/order`, `/target`의 `wait`는 최대120초다. HTTP 클라이언트 타임아웃을 그보다 길게 잡고, 대기 때문에 주행·인식을 멈추지 않는다. `accepted:false`이면 `reason`을 확인하고 다시 요청한다.
- M1은 결과3종을 한 번에 보낸다. 예를 들어 목표거점만 나중에 다시 보내면 앞서 보낸 표적·탐색 섹터가 비워질 수 있다.
- M3 객체6종은 `military_truck`, `mortar`, `tank`, `missile`, `ammo_box`, `drum`이다. 섹터는 `B-S1`~`B-S3`, `CM`, `R-S1`~`R-S3`. UGV 자체를 `tank` 객체로 세는 것이 아니라 판에 붙은 전차 그림을 뜻한다.
- 드론 영상의 신선도는 `X-Captured-At`으로 확인한다. 기본1초 간격이며 자기 진영 시설물 파괴가 누적되면2초·5초로 느려지고,3개 파괴 시 수신할 수 없다. 더 자주 호출해도 새 이미지가 빨리 만들어지지 않는다.
- 진행 종료 때 서버 상태가 먼저 `phase:reporting`으로 바뀌고 로봇에 `report`가 전달된다. 이때 M1·M3 제출은 닫히고 M6만 가능하다. 이후 `phase:finished`에서는 추가 보고를 받지 않으며, 자료상 그 뒤에 프로그램 종료 단계가 이어진다. 서버가 프로세스를 자동으로 강제 종료하는 방식인지는 설명하지 않았다.

| 미션 | 내용·채점 | 제출·마감 |
| --- | --- | --- |
| **M1** | 전술명령 해석 **10점**: 지정표적3+탐색 섹터3+목표거점4. 주최측 텍스트 LLM API 활용 | 진행 중 POST, 마지막 제출 채점 |
| **M2** | 지정표적 타격 **15점**: 유효타격10+연합 달성5 | 참가팀 서버 보고 없음, 센서 판정 |
| **M3** | 객체 인식 **30점**: 상대 진영3구역 각7+공통CM9. 종류와 개수 완전 일치 | 진행 중 POST, 마지막 제출 채점 |
| **M4** | 상대 UGV 타격·아군 생존 **최대15점**. 아군 피격0/1/2/3/4회 이상이면15/12/8/3/0점 | 참가팀 서버 보고 없음, 장치 판정 |
| **M5** | 목표거점 점령 **10점**. 먼저 점령한 연합의3팀 각10점, 점령 즉시 경기 종료 | 경기4:00에 GET으로 목표 수신, 센서로 점령 판정 |
| **M6** | 상대3팀 위험도 순위 **최대15점**. 전체 일치15, 1순위만 일치10, 2·3순위 중 하나 일치5 | 종료 후 서버 보고 단계부터 **30초**, 마지막 제출 채점 |

- 별도 연합 승리 점수는 이긴 연합의3팀 각5점이며, 무승부 시 양쪽 모두5점이라고 화면에 표시된다.
- **검산:** M1~M6의 최대점수 합은 **95점**이다. M5 화면에는 여기에 **별도 연합 승리5점**을 더한다고 명시되어 있어 최대100점의 구조로 읽힌다. 이 경기 점수를 최종평가의 **임무평가80%**로 환산하는 구체 산식은 이번 영상에서 제시되지 않았다.
- M4는 수광부에2초 연속 비쳐야 유효피격이고, 피격 후10초 무적이다. 아군이 쏴도 피격으로 센다.
- M6의 화면상 위험도 기준은 **남은 목숨/4 + 남은 탄/8 + M3점수/30**이다.
- **호출부호 `R-2`와 섹터 `R-S2`는 다르다.** M6 `ranking`에는 상대 진영 호출부호를 적는다.
- M1·M3·M6를 마감까지 보고하지 않으면 해당 항목0점이다. M6용 순위는 경기 중 미리 갱신해 두고 종료 신호를 받으면 바로 제출하는 흐름이 제시된다.

## 불일치·확인이 필요한 부분

- **늦은 입소 기준:** 화면의 일반 문구는 ‘입소식 종료 후 과제 수행이 시작되면 참가 불가’이고, 운영진 구두 설명은 ‘늦어도 정오 안에 도착, 정오 이후 참여 어려움’이다. 입소는 오전10시를 기준으로 준비하는 것이 안전하다.
- **점심 시간:** 화면은 **11:40~12:30**이다. 07:45 부근의 초벌·추가 음성인식 결과는 ‘그게11시40분까지여서’로 나와 시작·종료의 표현이 화면과 일치하지 않는다. 이 요약의 식사 일정은 화면을 근거로 적었으며 현장 시간 안내를 확인해야 한다.
- **충전기 사양:** 본문·주의사항과52분 구성품 라벨은 **12.6V/2A**다. 배터리 사양 표의 한 칸은 `12A`처럼 보이는 불일치가 있어 그 한 칸을 기준으로 해석하지 않았다.
- **LLM 사용 범위:** M1 화면에는 주최측 제공 API가 **‘텍스트 LLM만’**이라고 표시된다. 이번 음성에서는 **다른 API의 사용 허용·금지를 확정하는 추가 답변을 확인하지 못했다.** 제공 API의 기능 범위를 외부 API 전면 금지 규칙으로 확대해 해석하지 않았다.
- **자료의 날짜·버전:** 영상은11/6이지만 단계별 API 자료에는11/4 기준이라고 적혀 있다. 멘토도53:28~54:00에 OT 때 최종 문서를 다시 제공한다고 명시했다.
- **질문 속 과거 표기:** 57분 질문의 `goal_base`, `SUPPLY_BASE`, `CHARLIE/DELTA` 등은 혼선을 지적하는 문맥이다. 현재 구현값으로 그대로 채택하지 않았다.
- **시간표시 한계:** 화면만 확인한 구간의 시각은 해당 화면을 본 표본 위치이며 실제 발언 시작 시각과 몇 초 차이가 날 수 있다. API 예제와 숫자는 화면을 근거로 보완했다.
